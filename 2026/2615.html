背景

为了适应云上可动态伸缩的网状代理架构，以及出海跨大区走公网传输的需求，我之前对 libatbus 做了一轮幅度不小的重构：补齐了加密与压缩，引入了拓扑驱动路由，并重新梳理了节点关系和多路连接。两篇设计文章分别记录了 libatbus 的路由与协议变更 和 libatapp 的连接管理与自动重连。

上一次压测已经是十年前，当时测的还是裸通道。现在游戏服务端里的 RPC 频率高得多，单条消息也会带上链路跟踪和更复杂的元数据，所以我把这次测试的最小包长定在了 200 B。更小的包没有单独跑。TCP（io_stream）通道对不超过 7 KB（ATBUS_MACRO_DATA_SMALL_SIZE = 7168）的消息会自动合包，单次合并上限约 64 KB；200 B 无加密无压缩单核已经跑到 360 万 QPS 以上，更小包长的 QPS 只会更高，不会成为带宽瓶颈。

这次直接跑完整的 atbus::node v2 协议栈（帧封装、Protobuf、握手、X25519 密钥交换、加密和压缩），把跨平台基线、内存分配器、加密压缩组合、共享内存以及 2 到 1000 节点的多连接汇聚都完整测了一遍，方便不同部署场景对照选型。

现代化硬件设施基本都支持加密算法的硬件加速，性能会块很多。是否支持chacha20系的硬件加速还取决于设备型号，需要谨慎选择加密算法。 合理设置加密算法后，几乎对性能没什么影响。所以建议是全场景都开启，即便是在公司内网下（防止意外情况被其他业务嗅探和中间人攻击）。 压缩算法支持硬件加速的较少，所以建议根据成本来选择。对于跨大区网络或者专线带宽特别贵的还是可以开压缩来换取降低成本。

测试环境与方法

压测基于 libatbus 静态构建（动态库构建在 200 B 下会低约 22.5%，本文数据全部取自静态构建）。分别统计Linux、Windows、WSL2下的性能数据，方便对比各个平台的损耗。

单对基线是 1 发 1 收，走真实的 ctrl + data 双连接；多节点汇聚是 1 个单线程接收节点对接 1 / 9 / 99 / 999 个发送进程（总节点数 2 / 10 / 100 / 1000）。发送端按固定包长全速发包，写满发送缓冲区（单对默认 8 MB，1000 节点下调为 1 MB 以控制总内存）后等排空再继续；接收端全速收包并校验消息头的 8 字节递增序号。测试负载用固定随机种子生成的类 JSON 文本，加密握手走 X25519 + HKDF-SHA256，默认每 3 小时刷新密钥，单组 10～15 秒内不触发重协商。

文中 QPS 指接收端每秒收到的应用消息条数，吞吐量按接收端交付的原始 payload 字节数计算，不含协议头、加密膨胀或压缩缩减。单对每组跑 15 秒、多节点跑 10 秒，去掉前 2 秒建连预热和收尾残缺样本后，按样本实际时长加权取中位数。需要注意的是，TCP 通道测试在多次运行间存在高低两档波动：Linux 同机复测多数配置偏差在 10% 以内，8 KB 档可达 25%；Windows TCP 约两成配置偏差超过 20%。

我的机器跑WSL2和Windows测试时可能后台其他进程负载不稳定，会影响结果。但是量级时可以参考的。Linux机器时独立benchmark专用的虚拟机，数据是准确的。

跨平台基线与内存分配器

跨平台 TCP 基线

Linux 单核在 200 B 下收到 366 万条/s（697.5 MB/s），到 300 KB 时降为 9,645 条/s，吞吐升到 2.76 GB/s。小包吃满 CPU 的是逐条协议处理，大包拼的是内存拷贝和分配效率。

两边都换上 mimalloc 后，WSL2 和独立 Linux 的走势贴得很近：110 组完整矩阵的 WSL2 / Linux 比值中位数是 104%，104 组落在 85%～118% 之间，拿 WSL2 做日常开发和回归压测基本够用。唯一异常的是 8 KB 档，WSL2 无论用 glibc 还是 mimalloc 都停在约 1.06 GB/s，差不多只有独立 Linux（1.74～2.30 GB/s）的一半，原因还没查出来。Windows 原生 TCP 则明显偏慢，各包长下只有 Linux 的 14%～25%（64 KB 仅 382.9 MB/s），收发两端 CPU 都跑在 96%～99%，瓶颈主要在 Windows socket 的系统调用开销（libatbus已经自带了小包合批的功能，这里已经是小包合批大幅降低系统调用后了，Windows网络性能仍然差非常多）。

110 组里 mimalloc 在 85 组跑得更快，未压缩的大包路径（明文和 AES-GCM）吞吐直接涨到原来的 2.0～2.4 倍。根因在 atbus_connection_context.cpp 的 pack_message_with()：每条消息打包都会申请临时缓冲区（即使没开压缩，目前也会给 compressed_buffer 预留和消息体一样大的空间），大包高频申请和释放把默认 glibc ptmalloc 的开销放大了。换用 mimalloc 的代价是 200 B 小包略降约 9%，两端峰值 RSS 各多出约 6～21 MB。一旦开了压缩，CPU 大头都花在压缩算法上，分配器就不再是主要瓶颈。

加密与压缩开销

加密算法与平台差异

先看 Linux TCP 无压缩时 6 种加密配置在 5 档包长上的表现：

Linux TCP 无压缩下六种加密配置的 QPS 与吞吐量

Linux（mimalloc），无压缩。裸 ChaCha20 在 300 KB 时仅 337 QPS，因此 QPS 对数轴下限取 100。

在支持 AES-NI 的 Linux 上，AES-GCM 的大包损耗很小：64 KB 档明文 2.60 GB/s，开了 AES-GCM 还有 2.26～2.29 GB/s（只降 12%～13%）；200 B 小包因为每条消息的固定加解密和认证头占比高，QPS 从 366 万降到 162～164 万（约降 55%）。128 / 192 / 256 三种 Key 长度差距在 1% 左右，按安全规范选就行。ChaCha20-Poly1305 在 64 KB 下能跑到 1.65 GB/s（明文的 63%），适合没有 AES-NI 的环境。

至于裸 ChaCha20，在 Linux 上直接掉到 102 MB/s（只有明文的 3.8%），既慢又没有认证标签，生产环境不要选。代码里它和 ChaCha20-Poly1305 走的也不是同一套后端：裸 ChaCha20 路由到了 libsodium，而全局初始化函数只做了 OpenSSL 初始化，没有调用 sodium_init()，业务侧不手动初始化时连运行期 SIMD 优化都没开起来。

压缩及叠加加密

协议栈在 _allow_compress() 里限定了数据消息序列化后的 body 达到 1,024 B 才尝试压缩，且压缩后确实变小才输出压缩帧（200 B 和 256 B 直接跳过，因为包太小加上压缩字典和头部反而更占空间）。处理顺序固定为先压缩、再加密。

Linux TCP 下无压缩、LZ4 与 zstd 单独及叠加加密后的 QPS 与吞吐量

Linux 64 KB 上，LZ4 再加 AES-128-GCM 只降 1.3%（1.21 -> 1.19 GB/s），zstd 再加 AES-128-GCM 几乎看不出差别。到了 Windows 大包上甚至会出现“先压缩再加密比单独加密快得多”的现象：300 KB 档 ChaCha20-Poly1305 单独加密只有 136.2 MB/s，叠加 LZ4@default 后直接涨到 423.7 MB/s（接近明文 450.0 MB/s），AES-128-GCM 也从 81.4 MB/s 涨到 268.0 MB/s，本质是压缩省掉了一大半加密和操作系统拷贝字节量。

跨区部署时可以按带宽和单核能力算一笔简单的账：设链路可用带宽为 B、压缩后体积比例为 r，链路每秒大约能撑 B / r 的原始负载。按本测试文本粗估：1 Gbps 专线（线速约 119 MB/s）开 LZ4 后链路能撑约 270 MB/s，远低于 LZ4 + AES-128-GCM 单核 1.19 GB/s 的能力；开 zstd 后链路约 496 MB/s，刚好接近单核 525 MB/s。换成 10 Gbps 内网（线速约 1,192 MB/s），不开压缩的 AES-128-GCM（2.29 GB/s）就能打满网卡，默认开压缩反而会让 CPU 先顶满。上线前仍建议拿真实业务报文测一遍 r，随机二进制或已压缩数据没必要开压缩。

另外有一个当前实现里的细节需要说明，为了统一配置方式，我们目前是预定了一些压缩级别策略，映射到不同压缩算法时压缩率设置时不一样的。但是default对应的都是各个压缩算法的默认值。

Windows 上共享内存收益最大：绕开 socket 后，1 KB 就是 TCP 的 3 倍，8 KB～300 KB 直接涨到 5.4～5.6 倍，单核稳定输出 2.06～2.39 GB/s。Linux 上则不是所有包长都适合切共享内存：8 KB 以上 shm:// 确实比 TCP 快 7%～26%（64 KB 跑到 3.09 GB/s），但 200 B 和 1 KB 反而慢了 27% 和 9%。原因在于 TCP 会把 <= 7 KB 的小包合并发送摊薄开销，而 shm:// 逐条写入独立消息块并算校验。

共享内存内存操作比TCP慢的原因是共享内存通道支持多写单读，所有的操作都是原子操作，会导致CPU Cache Line失效而降低性能。 而它的优势在于crash恢复时消息不丢，以及因为支持多写所以不需要每两两连接都设置单独的缓冲区，某些场景仔细规划后会更省内存。

内存占用也要算进成本里。每个共享内存段默认映射 256 MB，挂上之后收发两个进程的峰值 RSS 都会从 11～40 MB 涨到约 267～271 MB（物理页两进程共享，宿主机不会扣双份内存）。如果业务要求本机通信也必须加密，还是得走 TCP。

多节点汇聚扩展（2 至 1000 节点）

我们还要测试高连接数时的性能衰减，所以有了这个汇聚场景测试：1 个单线程接收节点绑在独立物理核上，对接 1 / 9 / 99 / 999 个发送进程（总节点数 2 / 10 / 100 / 1000），20 种组合 × 6 档包长共 480 组。

先看无加密无压缩下，连接数放大 500 倍后单接收核的聚合能力：

Linux TCP 无加密无压缩在 2、10、100 和 1000 节点下的聚合 QPS 与聚合吞吐量

Linux（mimalloc），单线程接收节点聚合读数。

四条曲线基本贴在一起：200 B、256 B 和 300 KB 从 2 节点扩到 1000 节点几乎没有衰减（1000 节点下 200 B 仍有 370 万 QPS / 706.6 MB/s，300 KB 仍有 9.4K QPS / 2.70 GB/s）。1 KB 和 32 KB 随着连接数增加下降了约 17% 和 11%（1 KB 从 1.67M 降到 1.39M，32 KB 从 82.0K 降到 73.2K），多连接下接收端单消息耗时增加的具体热点还没采样定位。

上述数据分析结论：压缩比解压慢得多。1 发 1 收时，发送端先把单核跑满了；一旦有 10 个以上发送端并行压缩，发送端不再受限，而接收端解压速度远快于单核压缩，总吞吐立刻跳上一大截，之后在 10 到 1000 节点间保持平稳。在 1000 节点 300 KB 档，纯 LZ4 直接追平了无压缩（都是 2.70 GB/s）；LZ4 + AES-128-GCM（2.53 GB/s）甚至反超了不压缩的 AES-128-GCM（2.31 GB/s），因为接收端要解密的密文少了一多半，而 LZ4 解压代价很低。

测试边界

拿这组数据做容量估算时，有几个要注意的点：

  • 未测延迟分位（P50 / P99）：本轮全是压力打满的压测，发送缓冲一直写满，不能代表常规负载下的 RPC 延迟，延迟分布需要按固定发包速率单独测。
  • 全是本机链路：没经过真实网卡、交换机和公网丢包，结果反映的是协议栈和内核在单核上的 CPU 上限。（实际评估还要带上系统协议栈开销。按照经验Linux如果网卡带硬件加速，网络协议栈开销几乎不会打到CPU上，如果没有的化大约每 1Gbps占用 x86单核 20% 左右的CPU，ARM的化大约50%左右。具体还要用实际的硬件真实评测，这里只给个参考。libatbus的开销是低于系统协议栈处理的。）
  • 都是单向直连：没测多跳代理转发、双向同时满载。双向同时满载时通常承载减半。
  • 负载是单一可压缩文本：如果业务报文是随机二进制或已压缩资源，压缩率和压缩吞吐都会更低。

另外有三个测出来但还没定位根因的现象，留作后续排查：

  1. WSL2 在 8 KB 档无论用 glibc 还是 mimalloc 都停在约 1.06 GB/s，约为独立 Linux 的一半。猜测可能受Windows驱动或虚拟化影响。
  2. Windows TCP 下 AES-GCM 降幅偏大（仅为明文的 17%～40%），反而慢于 ChaCha20-Poly1305。
  3. 多节点汇聚时，1 KB 和 32 KB 的非压缩组合随连接数增加下降了 11%～17%。猜测可能受缓存命中率和系统调度策略影响。

总结

这轮完整协议栈压测把测试了 libatbus 的极限性能：200 B 下接收端能稳住 360～370 万 QPS，大包 TCP 跑到 20Gbps 、共享内存跑到 24 Gbps；大包场景换 mimalloc 提升明显；内网高带宽默认别开压缩，跨区带宽紧张时先压缩再加密基本不额外拖慢加密；多发送端汇聚到中心节点时，瓶颈会从发送端压缩转到接收端解压，LZ4 甚至能在大包加密场景下反超不压缩。

顺着压测结果，协议栈后续还有几处可以考虑的优化点：更精细的压缩级别控制，不开压缩时优化缓冲区管理，根据压测结果调整默认的加密和压缩算法优先级。除此之外，也可以接着 《面向 CPU 缓存命中率的 AC 自动机优化》 的思路，继续抠收发热路径上的内存分配和缓存命中率。这些就以后慢慢来吧。
